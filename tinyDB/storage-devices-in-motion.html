Before the device

What happens between read() and the hardware

Every device below receives the same kind of thing: a request for a numbered run of sectors, called logical block addresses (LBAs). The operating system turns your file read into those numbers first. Here is one concrete trip, with the numbers worked out.

Say a storage engine wants page 128 of orders.db, with 8 KB pages, on a filesystem with 4 KB blocks and a disk with 512-byte sectors.

  1. Application calls pread(fd, buf, 8192, offset).offset = 128 × 8,192 = 1,048,576 bytes
  2. Page cache checks whether those bytes are already in RAM. On a miss, the kernel must go to the device.file blocks = 1,048,576 ÷ 4,096 = block 256 and 257
  3. Filesystem looks up the file's extent map: file block 0 starts at disk block 9,000,000.disk blocks = 9,000,000 + 256 = 9,000,256 … 9,000,257
  4. Block layer converts to sectors and queues one request. The I/O scheduler may merge it with neighbours or reorder the queue.LBA = 9,000,256 × (4,096 ÷ 512) = 72,002,048 · length = 16 sectors
  5. Driver sends a command (SATA/AHCI or an NVMe submission queue entry) and gives the device a DMA address in RAM.READ LBA 72,002,048, 16 sectors → DMA to buffer
  6. Device maps the LBA to something physical. A tape locates a block position, a disk maps it to a track and sector, an SSD's FTL maps it to a NAND page. This is the part the simulators show.
  7. Completion: the device writes the data into RAM by DMA, raises an interrupt, and the kernel wakes the waiting process.
Device 1 · sequential access

Tape: fast when streaming, slow when searching

A tape cartridge holds a single long ribbon of magnetic tape wound on one reel. The drive threads it past a fixed read/write head onto a take-up reel inside the drive. The head never moves along the tape; the tape moves past the head. To reach a block, the drive has to physically wind the tape there.

That gives tape two very different speeds. Once it is positioned, it streams data faster than most hard disks. But reaching a random block means winding hundreds of metres of tape, which takes tens of seconds.

Model values: each block is 5 m of tape holding 1 GB, the drive winds at 10 m/s while locating, and needs 1.2 s to stop, reverse and settle before each locate. The reel hub radius is 22 mm and the tape is 5.2 µm thick. Real drives also move the head across many parallel track bands ("wraps") and run the tape back and forth in a serpentine path; this model keeps one band so the geometry stays readable.

Device 2 · mechanical random access

Hard disk: an arm, a spinning platter, and waiting

A hard disk stores data on circular tracks on a spinning platter. Each track is cut into sectors. An actuator arm swings the head between tracks. Reading one sector costs three things in sequence:

Seek: swing the arm to the right track. Rotational latency: wait for the sector to spin under the head. Transfer: let the sector pass under the head.

Outer tracks are longer, so modern drives put more sectors on them (zoned bit recording). This simulated platter does the same: track T0 near the centre has 8 sectors, and T4 near the edge has 24. One revolution therefore delivers three times as much data on T4 as on T0.

The platter is spinning before you press Time IO, so where it happens to be decides the rotational waits. Run the same workload twice and the waits change, which is exactly what happens on a real drive. The seek formula is a toy model for a five-track disk; a real drive has hundreds of thousands of tracks and the same square-root shape.

Compare hello.txt with report.txt. Both are small files. hello.txt sits in eleven neighbouring sectors, so after one seek the bytes arrive back to back with no rotational wait. report.txt is fragmented across four tracks, and nearly all of its time goes to seeking and waiting. This is why defragmenting helped hard disks, and why databases try to allocate pages in contiguous extents.

Inside the OS

How the OS orders disk requests

When several requests are waiting, the order in which they are sent decides how far the arm travels. The block layer's I/O scheduler picks that order. The classic algorithms, all measured in cylinders (tracks) the head crosses:

FCFS serves requests in arrival order. SSTF always goes to the closest request next; it is short but can starve far-away requests. SCAN (the elevator) sweeps in one direction to the end of the disk, then reverses. C-SCAN sweeps one way, then jumps back to the start and sweeps again, giving more even wait times. LOOK and C-LOOK are SCAN and C-SCAN that turn around at the last request instead of the disk edge.

Device 3 · no moving parts

SSD: parallel flash chips and a translation layer

An SSD has nothing to seek and nothing to spin. A controller talks to several NAND flash dies over independent channels. Each die holds blocks, and each block holds pages (typically 16 KB). Three rules shape everything an SSD does:

Reading a page is fast, about 50 µs for the chip to sense it. Writing (programming) a page is slower, several hundred µs. And a page cannot be overwritten in place: it can only be written after its whole block has been erased, which takes milliseconds.

So the controller's flash translation layer (FTL) keeps a map from each LBA to the page that currently holds it. An overwrite goes to a fresh page, the map is updated, and the old page is marked stale. Later, garbage collection copies the still-valid pages out of a dirty block and erases it to make room.

The extra page copy during garbage collection is write amplification: the flash wrote more than the host asked for.

Back to the storage engine

Why databases care about all this

B+ tree lookups are random reads. Each level of the tree is one page somewhere in the file. On a hard disk, a three-level lookup that misses the buffer pool can cost three seeks plus three rotational waits, around 35 ms. That is why disk-era databases keep the upper levels of every index in memory, and why a large buffer pool mattered so much.

The write-ahead log is a sequential append. On a hard disk the log head stays on one track region, so a commit is mostly a rotational wait instead of a seek. Putting the WAL on its own disk was standard advice for that reason.

Page size is a device decision. An 8 KB or 16 KB page amortises one access cost over more rows. On an SSD, a page that matches the NAND page size avoids partial-page reads and extra writes.

SSDs reward concurrency. One read at a time leaves most dies idle. Issuing several page reads at once (prefetching, parallel scans, io_uring or NVMe queues) is how engines reach the drive's rated IOPS.

SSDs dislike scattered overwrites. Updating pages in place makes the FTL leave stale pages everywhere and run more garbage collection. Log-structured designs such as LSM trees write sequentially instead, which keeps write amplification low.
