Write-Ahead Log and Crash Recovery

The problem

Why a database keeps a log

A database never edits the data file directly. It reads a page into the buffer pool in RAM, changes it there, and writes it back later, whenever the buffer manager decides. Two policy choices decide what a crash can break.

Steal. May the buffer manager write a page to disk while a transaction that changed it is still running? If yes, a crash can leave uncommitted changes on disk. Recovery then needs undo.

Force. Must every page a transaction changed be written to disk before the commit returns? If not, a crash can lose committed changes that were still only in RAM. Recovery then needs redo.

Force (write pages at commit)No force
No steal (never write uncommitted pages)No undo, no redo. Commit waits on many random page writes, and every uncommitted page stays pinned in RAM.Redo only.
StealUndo only.Undo and redo. Fastest at run time. This is what almost every disk-based engine picks.

The write-ahead log makes steal plus no-force safe. Every change is first described in a log record that holds enough to redo it (the new value) and to undo it (the old value). The log is append-only, so writing it is sequential. A commit costs one sequential write and an fsync of the log, instead of random writes to every page the transaction touched.

WAL structure

Anatomy of a log record

The log is one long file of variable-length records. Each record starts with a fixed header, followed by a payload whose shape depends on the record type. This page uses a small, realistic format: a 32-byte header plus a 24-byte payload for page changes, all integers little-endian.

A record's LSN (log sequence number) is simply its byte offset in the log file. The first record is at LSN 0; a 56-byte record at LSN 0 means the next one starts at LSN 56. PostgreSQL and InnoDB number their logs the same way, as byte positions.

The prevLSN field links each transaction's records into a backward chain through the log: T1's COMMIT points to 56, which points to 0. Undo walks exactly this chain. The crc32 lets recovery find where the log really ends: after a crash the last record may be half-written, and the first record whose checksum fails marks the end. Bookkeeping

Six pointers and two rules

Recovery works by comparing a handful of LSNs. Every one of them appears in the simulator.

pageLSN
Stored in each page's header, on disk and in memory: the LSN of the newest log record applied to that page. It answers "does this page already contain change X?"
flushedLSN
The log is durable on disk up to this byte. Everything after it is still in the log buffer in RAM.
prevLSN
In each record: the same transaction's previous record. Forms the undo chain.
lastLSN
In the transaction table (RAM): each active transaction's newest record, the head of its chain.
recLSN
In the dirty page table (RAM): the first record that made the page dirty since it was last written. Changes older than this are already on disk.
master record
A small fixed spot on disk holding the LSN where the latest checkpoint begins. Recovery reads it first.
Rule 1 · write-ahead
before writing page P:
flushedLSN > pageLSN(P)

The log record describing a change must be on disk before the changed page is. Otherwise a page with an uncommitted change could reach disk with no before image anywhere to undo it.

Rule 2 · commit
commit returns only after
COMMIT record is durable

The transaction's pages can stay in RAM, but its COMMIT record and everything before it must be fsynced. Then redo can always rebuild the pages.

ARIES

Recovery in three passes

After a crash, RAM is empty. The disk holds a data file in an unknown mix of states (some pages too old, some holding uncommitted changes) and a log that ends somewhere. ARIES, the algorithm from IBM Research (Mohan et al., 1992) that most engines follow, repairs this in three passes.

1. Analysis: who was running, and which pages might be stale?

Start at the checkpoint named by the master record and scan forward to the end of the log. Rebuild the transaction table and the dirty page table as they were at the moment of the crash.

TT, DPT ← empty
for rec in log, from master.checkpointLSN to the end:
    if rec is END_CKPT:  add its saved TT and DPT entries
    if rec belongs to a transaction x:
        if rec is END:   remove x from TT
        else:            TT[x].lastLSN = rec.LSN;  if COMMIT: TT[x].status = committed
    if rec changes page P and P not in DPT:
        DPT[P] = rec.LSN                       // first change that may be missing
for each committed x still in TT:  write END, remove x
losers = every x left in TT              // were running at the crash

2. Redo: repeat history

Scan forward from the smallest recLSN in the dirty page table and reapply every change that did not reach disk, including changes of losers. After redo, memory looks exactly as it did the instant before the crash. Reapplying loser changes sounds wasteful, but it means the page state is always one the log can explain, so undo can work on it safely.

for rec from min(DPT.recLSN) to the end of the log:
    if rec is UPDATE or CLR on page P:
        if P not in DPT:          skip        // page was written after this change
        if rec.LSN < DPT[P]:      skip        // change is older than the page's dirtiness
        read P;  if pageLSN(P) ≥ rec.LSN: skip   // the page already has it
        apply rec.after to P;  pageLSN(P) = rec.LSN

The first two checks avoid reading pages from disk at all. The third, the pageLSN test, is what makes redo safe to repeat any number of times: a change is applied only if the page is older than the change. Real records are often not idempotent ("insert a row into slot 4"), so this test is required, not an optimisation.

3. Undo: roll back the losers, newest first

ToUndo = { lastLSN of every loser }
while ToUndo is not empty:
    L = max(ToUndo);  rec = log[L]                  // one backward sweep
    if rec is UPDATE:  write CLR(page, rec.before, undoNext = rec.prevLSN); apply it
                       next = rec.prevLSN
    if rec is CLR:     next = rec.undoNextLSN          // already undone earlier
    if rec is ABORT:   next = rec.prevLSN
    if next is none:   write END for rec's transaction
    else:              replace L by next in ToUndo

Every undo action writes a CLR (compensation log record). A CLR is redo-only: it carries the restored value and undoNextLSN, the next record of that transaction that still needs undoing. If the system crashes again in the middle of undo, the next recovery redoes the CLRs (so their work is back) and, reaching a CLR during undo, jumps straight to its undoNextLSN. No change is ever undone twice, and the total undo work is bounded even if the system crashes over and over. Scenario 3 in the simulator shows exactly this.

Taking the largest LSN each time means the undo pass reads the log in one backward sweep, even when several losers are interleaved.

Bounding the work

Checkpoints

Without checkpoints, analysis would scan the log from byte 0. A fuzzy checkpoint fixes that cheaply: it writes BEGIN_CKPT, then an END_CKPT holding copies of the transaction table and dirty page table, forces the log, and updates the master record. It does not stop transactions and does not write any data pages.

Two LSNs then bound recovery. Analysis starts at the checkpoint. Redo starts at the smallest recLSN in the dirty page table, which can be earlier than the checkpoint. That is why databases also run a background writer that keeps flushing old dirty pages: each flush removes a page from the dirty page table, moves the redo start forward, and lets the log before it be recycled.

The log can be truncated before min(redo start, first LSN of the oldest active transaction). Anything older is no longer needed for either redo or undo.

In practice

How real engines do it

PostgreSQL writes WAL records with a 24-byte header (total length, transaction id, pointer to the previous record, resource manager id, CRC) into 16 MB segment files. Its recovery is redo only. It needs no undo pass because of MVCC: rows written by a transaction that never committed stay on disk but are invisible, since the commit log (pg_xact) does not mark it committed. To protect against torn pages, the first change to a page after each checkpoint logs a full image of the page (full_page_writes).

MySQL InnoDB splits the job in two. The redo log records physical changes to pages, numbered by a byte-based LSN. Undo information lives in undo tablespaces, and changes to those undo pages are themselves redo-logged. Recovery replays the redo log, then rolls back incomplete transactions using undo, partly in the background. A doublewrite buffer guards against torn page writes. With the default innodb_flush_log_at_trx_commit=1, every commit forces the log.

SQLite in WAL mode appends whole page images as frames to a separate -wal file. A frame that carries the database size marks a commit, and cumulative checksums mark where valid frames end. Pages reach the main database file only when a checkpoint copies committed frames back. Uncommitted pages never touch the main file (no steal), so SQLite needs no undo either.

The approach in this simulator, with physical before and after images, prevLSN chains and CLRs, is classic ARIES. It is closest to what IBM Db2, SQL Server and InnoDB do.

For your storage engine

Building it into your own engine

  1. Put pageLSN in the page header. In a slotted page, it sits next to the slot count and free-space pointer. Update it on every change, under the page latch.
  2. Log before you modify. Build the record with before and after images, append it to the log buffer to get its LSN, then change the page and stamp that LSN.
  3. Enforce the WAL rule in the buffer manager. Before evicting or writing a dirty page, flush the log up to its pageLSN.
  4. Force at commit, in groups. One log-writer thread can batch many transactions' COMMIT records into a single fsync.
  5. Checksum every record. Recovery must find a half-written tail and stop there.
  6. Handle B+ tree splits as their own atomic action. A split changes several pages. If the transaction that caused it aborts, undo should not unsplit the tree, because other transactions may already be using the new pages. ARIES logs splits as a "nested top action" that commits on its own.
  7. Guard against torn pages. A 16 KB page write can be interrupted halfway. Use page checksums plus full page images in the log (as PostgreSQL does) or a doublewrite area (as InnoDB does).
  8. Test by crashing. Inject a crash after every log append and every page write, run recovery, and check that committed data is present and uncommitted data is gone. Then crash during recovery and check again.
